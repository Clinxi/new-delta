# 技术说明

## 架构

系统由一个 Node.js 服务和三个网页组成。服务负责验证入场数据、保存场次、主持鉴权及状态推送；手机提交资料，每 2 秒查询本人和全局摘要，大屏和控制台通过 Server-Sent Events（SSE）接收完整状态快照。

```text
手机参与页 ── POST /api/join ──────────┐
    └──── 每 2 秒 GET /api/status ────┤
                                     │
主持控制台 ── 受保护的控制接口 ────────┼─ Node.js 单进程 ─ 本地数据文件/上传图片
                                     │
大屏 / 控制台 ◀────────── SSE ────────┘
```

服务只支持一个活动场次、一份权威状态和一个写入进程。多个浏览器可以查看同一大屏，但多个服务实例不能直接共享当前文件存储。

## 核心状态

```text
waiting ── 主持开始 ──▶ countdown ── 服务器时间到 ──▶ launched
   ▲                       │                           │
   └────── 主持复位 ────────┴───────────────────────────┘
```

- `waiting`：开放入场，手机可提交或更新本人资料。
- `countdown`：关闭新入场，客户端根据服务器时间和 `countdownStartedAt` 计算剩余时间。
- `launched`：展示启动完成效果，主持可复位或清空场次。

清空场次会更换 `eventId`；旧手机资料标识不再属于新场次。保留嘉宾复位用于同场重演。

## 页面

| 路径 | 说明 |
| --- | --- |
| `/stage.html` | 公开大屏，适配浏览器全屏展示 |
| `/join.html?event=...` | 公开手机参与页，场次标识来自控制台生成的链接 |
| `/admin.html` | 主持控制台，控制接口需要登录 |

部署在域名根路径。静态页面与 API 必须同源；未配置跨域访问。

## 主要接口

请求和响应使用 JSON，二维码接口除外。错误应由调用方显示给操作者，不应把失败当作成功。

| 方法与路径 | 用途 | 访问要求 |
| --- | --- | --- |
| `GET /api/state` | 获取当前完整快照 | 公开 |
| `GET /api/info` | 获取当前手机入场和大屏地址 | 公开 |
| `GET /api/status?participantId=...` | 获取手机轻量状态；可选参数指定本人 ID | 公开；只返回最多一条参与记录 |
| `GET /api/events` | SSE `state` 事件，连接恢复后获取最新状态 | 公开 |
| `POST /api/join` | 加入或以本人标识更新资料 | 有效场次、等待阶段、同意展示 |
| `GET /api/qr.svg?text=...` | 生成入场链接二维码 | 公开，仅允许 HTTP(S) 链接 |
| `GET /api/admin/session` | 检查主持登录状态 | 公开返回鉴权结果 |
| `POST /api/admin/login` | 使用主持口令登录 | 正确口令 |
| `POST /api/admin/logout` | 注销当前主持会话 | 会话相关 |
| `GET /api/admin/info` | 获取手机、大屏及局域网地址 | 主持会话 |
| `POST /api/admin/settings` | 修改文案、主题、Logo、倒计时和公开地址 | 主持会话 |
| `POST /api/admin/launch` | 发起倒计时 | 主持会话、等待阶段 |
| `POST /api/admin/reset` | 复位或清空场次 | 主持会话 |
| `POST /api/admin/demo` | 添加演示嘉宾 | 主持会话、等待阶段 |
| `DELETE /api/admin/participants/:id` | 移除指定嘉宾 | 主持会话 |

入场请求示意：

```json
{
  "eventId": "从当前入场链接取得",
  "nickname": "嘉宾小林",
  "avatarDataUrl": "data:image/jpeg;base64,...",
  "consent": true
}
```

返回 `participant` 和 `participantToken`。后续更新将 `participantToken` 传回 `/api/join`，只能修改对应本人的资料。手机将该标识与场次一同保存在浏览器本地存储。

状态快照包含：

```text
eventId, version, serverTime,
settings { title, subtitle, launchText, theme, publicUrl,
           countdownSeconds, logoUrl },
phase, countdownStartedAt, launchedAt,
participants [{ id, nickname, avatarUrl, joinedAt, isDemo }],
participantCount, maxParticipants
```

SSE 使用完整快照，避免客户端在断线期间丢失增量后无法恢复。加入突发时，服务按 150ms 窗口合并广播中间状态，每次资料修改仍单独同步写盘。头像文件由 URL 引用，不在每次事件中重复传图片。反向代理必须关闭事件接口的响应缓冲。

手机端不订阅完整名单 SSE，而是每 2 秒请求 `/api/status`，返回全局人数、阶段、活动设置和最多本人的一条参与记录。这减少所有手机反复下载全量名单的开销；公开大屏接口仍可读取展示名单，不应将本人 ID 当作身份隐私保护机制。演示嘉宾用显式的 `isDemo: true` 标识，正式入场为 `false`，不会仅凭昵称判断身份。

## 输入与访问边界

- 昵称为 2–20 字符，页面渲染应按文本处理。
- 嘉宾主动上传图片；手机页通过 Canvas 裁成 256px 正方形并压缩，Logo 最长边压至 480px 并保留透明。原图不得超过 10MB。服务端限制单张图片 256KB，仅接收经文件签名和尺寸识别检查的 PNG、JPEG、WebP，宽高各不得超过 4096px，总像素不得超过 1600 万。
- 不提供任意外部图片 URL 代理，避免让服务代为抓取不受控地址。
- 主持口令由环境配置；登录后通过 HttpOnly、SameSite Cookie 保存会话，前端不持有主持口令令牌。
- 修改接口检查浏览器请求的来源，登录和入场请求有频率限制。
- 公开状态包含要在大屏展示的昵称和头像地址。参与链接不是实名资格凭证，获得链接的人可能加入。
- 当前版本没有内容审核队列，参与者名额不能代替身份核验或门票系统。

## 数据与恢复

数据目录由 `DATA_DIR` 指定，默认 `./data`。`state.json` 保存场次、设置、参与者、参与凭证哈希和时间戳，`uploads/` 保存头像与 Logo。服务会先写 `state.json.tmp` 再原子替换正式文件，没有自动历史备份。写盘失败时回滚内存状态并向请求返回 503；倒计时后台保存失败会每秒重试。原子文件替换可避免常见的写入中断导致半份 JSON。具体环境变量见 `.env.example`。

`启动.command` 调用 `scripts/start.mjs`，首次自动创建正式 `.env`（端口 `3188`，固定随机主持口令），已有配置则沿用。`npm start` 按现有 `.env` 运行，`.env.example` 中默认端口为 `3000`。`scripts/preview.mjs` 使用独立 `.preview-data/` 和演示口令 `preview-ceremony-only`，只监听本机，不能将该口令用于正式部署。

服务器恢复时读取已有状态；正在进行的倒计时沿用原时间戳，若倒计时已结束，应进入启动完成状态。重启不会自动创建新场次。

原子写入不等于磁盘灾难恢复。生产部署应确保数据目录可写、磁盘有足够空间，备份时先停止服务。若数据文件损坏，不应在没有人工核对的情况下把错误当成空场次继续启动。

更新头像、移除嘉宾或清空参与者后，服务会清理不再被引用的头像文件；仍在活动设置中使用的 Logo 会保留。清空场次后仍须检查人工复制的数据目录、服务器快照和历史备份。需要彻底清理时，停止服务，由操作人员确认并移除不再需要的数据副本；不要只清浏览器页面就认为后台资料已删除。

## 性能与扩展

默认软件人数上限是 1000。大屏同时渲染最多 180 个头像，超过时每 12 秒轮换一部分头像，以降低大量 DOM 动画的压力。状态广播合并突发变化后向大屏、控制台发送完整参与列表，手机接收轻量轮询结果。实际容量取决于网络、电脑、头像数量和大屏渲染性能。当前版本尚未完成 1000 人真实设备的现场负载测试，没有给出经压力测试的并发容量承诺。

需要进一步产品化时，可按需求扩展：

1. 多活动：活动表与权限模型、场次独立入场凭证。
2. 多实例：共享数据库、发布订阅服务、对象存储，移除单机文件写入假设。
3. 微信身份：申请并配置相应的正式平台能力；按微信当时的授权规则处理昵称和头像，不能把扫码直接等同于可取得微信头像。
4. 审核：资料待审核队列、主持审核通过后广播。
5. 正式运维：容量压测、监控、日志留存约定和数据清理策略。

## 验证方式

`npm test` 执行服务接口测试。前端验收需使用真实浏览器，至少覆盖：两台设备同步、首次加入、修改本人资料、无头像加入、断线恢复、倒计时刷新、复位、清场隔离、恶意文本和不合规图片被拒绝。

测试成功代表当前检查通过；LED 屏、移动网络、会场 Wi-Fi 和浏览器自动播放权限仍需现场彩排确认。
